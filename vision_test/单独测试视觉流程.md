# 单独测试视觉流程 (walk_kick_framework)

本文档用于只测试机器人 `dvision` 视觉模块, 不启动走路 / 踢球 / 跌倒恢复。
适用机器人: **192.168.99.103** (nvidia/nvidia), 代码目录 `~/walk_kick_framework`。

与完整 piplus_soccer 参考文档的区别:
- 目录路径换成 `~/walk_kick_framework/RoboCup_Workspace`
- 新增 **web 画面叠加** (浏览器看实时画面 + 球标记 + 眼睛/相机 与 base_link 坐标)
- 处理了 conda python 会破坏 ROS1 环境的问题(必须用系统 python3)

## 0. 一键启动(推荐)

在机器人上:

```bash
cd ~/walk_kick_framework/vision_test
./start_vision_test.sh
```

脚本会依次:
1. 清理旧进程
2. 检查/启动 roscore
3. **启动 ROS2 bringup (hightorque midware)** —— 读电机编码器得到**真实头部角度**
4. 启动 head 反馈链路: `/joint_states` → UDP 15002 → ROS1 MotorState →
   `publish_motion_info.py` → `/dmotion_X/MotionInfo` (dvision + overlay 自动用)
5. 以 `VISION_ONLY` 模式启动 dvision
6. 启动 web 叠加节点

完成后浏览器打开:

```
http://192.168.99.103:8090
```

画面包含: 实时相机图 + 画面中心十字 + 球(绿色圆/连线) + 左上文字面板
(见 §4.1)。停止用 `./stop_vision_test.sh`。

**环境变量:**
- `VISION_START_BRINGUP=0` 不启动 bringup(纯视觉, 头部角度=0)
- `VISION_MOVE_TO_ZERO=1` 启动后 move_to_zero(默认 0=不归零, 读取当前头部姿态)

> 注意: 带 bringup 运行会**给电机上电**。dvision 需要独占 ZED 相机。若之前跑过
> `start_all.sh`, 先执行 `cd ~/walk_kick_framework && ./stop_all.sh` 或让脚本自动清理。

## 4. 画面与坐标含义

### 4.1 web 画面(推荐)

- 画面中心十字 = 相机光轴中心
- **绿色圆** = 检测到的球(由 `VisionInfo.ball_global`(camera FLU) 用 ZED 真实内参投影,
  不经 ballTrack, 所以框得准)
- 左上文字面板:
  - `mode`: `VISION_ONLY`(单独测试) 或 `REALWORLD`
  - `see_ball`: 是否看到球
  - `ball_quality`: 球检测置信度
  - `base_link(m)`: 球相对机器人 `base_link`, **米**。由 camera FLU 做 FK 得到,
    FK 用头部 yaw/pitch(见下)
  - `eye(camFLU,m)`: 球相对相机, 米(x前/y左/z上) = `VisionInfo.ball_global`
  - `head yaw/pitch`: 计算 base_link 时使用的头部角度

**头部角度来源**(决定 base_link 是否准):
- 有 `/dmotion_X/MotionInfo`(dancer-io 在跑)→ 自动订阅真实头部角度
- 单独测试(无 motion 反馈)→ 默认 0。**单独测试里动头部, 必须告诉 overlay 实际头部角度**,
  否则 base_link 会随头部变化(球固定但 camera 系坐标变了, FK 却按 0 算)。live 设置:
  ```bash
  rosparam set /vision_head_yaw_deg <实际yaw度>
  rosparam set /vision_head_pitch_deg <实际pitch度>
  ```
  或启动时静态传: `python3 vision_web_overlay.py --head-yaw-deg 10 --head-pitch-deg -15`
- FK 数学已验证自洽: 球固定 + 给对头部角度 → base_link 恒定(与 zed_dvision.cpp 一致)
- 内参: ZED-M VGA(672×376) 真实值 fx=fy=363.27, cx=336.26, cy=190.27
  (camera.yml 的 640×480 值不适用)

> 若要做"动头部时 base_link 恒定"的验证, 最干净的方式是跑完整框架
> (`cd ~/walk_kick_framework && ./start_all.sh`)—— 有 dancer-io 提供真实头部反馈。

状态文本接口(终端):

```bash

```

### 4.3 base_link 坐标

```bash
rostopic echo /dvision_1/VisionInfo/ball_field
```

- 原点: 机器人 `base_link`
- 单位: **米** (本框架 dvision 已从厘米改成米制)
- `x`: 前方为正; `y`: 左侧为正; `z`: 上方为正

示例 `x: 0.52, y: 0.10, z: 0.19` 表示球在 base_link 前方约 52cm、左侧约 10cm、
高约 19cm。

> 注意: 与完整 piplus_soccer 参考文档不同, 本框架 `ball_field` 是**米**。
> `ros1_ball_position_udp_sender` 用 `BALL_FIELD_SCALE`(=1.0) 直通, ROS2 侧
> `/ros1_ball_position` 即米制。

### 4.4 眼睛(相机)坐标 = ball_global

`/dvision_1/VisionInfo/ball_global` 存的是原始 **camera FLU** 球坐标(米), 不受头部影响,
是 overlay 里 `eye(camFLU,m)` 与 FK 的输入。含义: 原点为相机; `x` 相机前方为正,
`y` 相机左侧为正, `z` 相机上方为正。

`base_link` 由 FK 计算(与 zed_dvision.cpp 一致), 含头部 yaw/pitch:

```text
R_base_head_pitch = R_z(yaw) @ R_y(pitch)
camera FLU -> left_eye optical: opt=(-Y,-Z,X)
R_base_left_eye_optical = R_base_head_pitch @ R_cam_optical
平移链: base->head_yaw(0.014,-0.000267,0.1981)->head_pitch(0,0,0.0275)
       ->camera_link(0.048925,0.005352,0.058472)->left_eye(0,0.0315,0)
```

## 5. 快速判断坐标是否合理

当头部 yaw/pitch=0 时, FK 退化为简单偏移(≈参考文档 §6):

```text
base_x_m ~= camera_x_m + 0.063
base_y_m ~= camera_y_m + 0.037
base_z_m ~= camera_z_m + 0.284
```

例: camera 测量 x=0.632, y=0.126, z=-0.173(m) → 估算 base_x≈0.695m, base_y≈0.163m,
base_z≈0.111m。若 `ball_field` 接近该结果, 说明相机到 base_link 转换基本正确。

## 6. 常见问题

### 6.1 rostopic echo VisionInfo 报消息类型错误

```text
ERROR: Cannot load message class for [dmsgs/VisionInfo]. Are your messages built?
```

当前终端没 source 工作空间, 重新执行第一节的三个 `source`。

### 6.2 VisionOnlyMode 被改回 False

不要只执行:

```bash
rosparam set /ZJUDancer/VisionOnlyMode true
roslaunch dvision 1.launch
```

`1.launch`/`zed_default.launch` 会重新加载 `global.yml`, 把参数覆盖回 `False`。
使用本目录的 `dvision_vision_only.launch`(先加载 global.yml 再覆盖)。

### 6.3 没有球坐标输出

先检查:

```bash
rostopic echo /dvision_1/VisionInfo/see_ball
```

如果一直是 `False`:
- 确认球在相机画面内
- 确认启动日志是 `VISION_ONLY mode`
- 确认 ZED 没有持续报抓帧失败
- 确认没有其他 dvision / ZED 程序占用相机

```bash
rosnode list
pgrep -af dvision
```

必要时清理后重跑 `./start_vision_test.sh`。

### 6.4 ZED 抓帧失败

日志可能出现 `Frames may be corrupted or degraded` / `ZED 抓取失败`。优先检查:
- ZED 是否被其他程序占用(旧 dvision / zed_ball_viser / soccer_backend 等)
- USB / 线缆 / 供电是否稳定
- 是否有旧的 dvision 节点没关

### 6.5 web 页面打不开 / 没画面

- 确认 `vision_web_overlay.py` 进程在: `pgrep -af vision_web_overlay`
- 确认 dvision 日志里有 `cam_image` 发布(`OfflineRecord=true` 才会发):
  `rostopic hz /dvision_1/cam_image`
- 确认 8090 端口没被占用: `ss -ltnp | grep 8090`
- 确认机器人 IP 是 192.168.99.103(局域网)

### 6.6 想同时看桥接后的 ROS2 球话题

框架正式运行时, ROS1 `ball_field` 会经 UDP 15003 桥到 ROS2 `/ros1_ball_position`
(见 `start_route_c_ros1_decision.sh` 的 `BALL_FIELD_SCALE`)。单独视觉测试不启动该桥。

## 7. 当前框架约定

- `/dvision_1/VisionInfo/ball_field`
  - `base_link` 坐标, **单位米**(本框架 dvision 已改米制; `BALL_FIELD_SCALE`=1.0 直通)
- `/dvision_1/VisionInfo/ballTrack`
  - 相机相对球需要的头部 yaw/pitch(度), web 用它投影球的像素位置
- `/dvision_1/cam_image`
  - 实时画面(仅 `OfflineRecord=true` 时发布), web 叠加的数据源
- 检测模型
  - `model/best26.engine`: **YOLO26s 单类(球)** TensorRT engine(FP16, 640×640), 由
    `best(2).pt` 导出 ONNX 后用 trtexec 构建
  - `model/hum.names`: 单类 `ball`
  - 检测器 `yolov26.cpp`: letterbox→TRT 推理→解码 [1,5,8400]→NMS→映射回原图
  - 门/角点/线等旧 7 类检测已停用(新模型只出球), 踢球方向 goal_yaw 会退化为正前方
